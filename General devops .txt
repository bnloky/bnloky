#DSOMM is the DevSecOps maturity model that is being developed at the OWASP foundation.
I was using DSOMM to evaluate DevSecOps maturity for a few startups as a thought exercise. No surprise that most of these were on Level 1 when it came to build & deployment. All of them failed miserably when it came to test & verification.
I think achieving Level 4 would be a pipe dream for most of the DevSecOps engineers in these places 😀
If you are a DevOps engineer or are interested in DevSecOps, I highly recommend evaluating where you currently stand using the DSOMM matrix.
The Evaluation matrix is available at https://lnkd.in/gPQCwHz7 More information on DSOMM is available at https://lnkd.in/g52eHp32

#Given a git repository, how do you take the code all the way to production? With the following requirements.
1. Must be deployable to multiple environments, in this case to Dev, Staging and Production.
2. Must be able to build and deploy without any human intervention other than approving a PR to specific branch
3. Must be able to make configuration changes consumed by the code without having to do a full deployment
4. Must incorporate basic security aspects such as credentials and container scans etc.
5. Must be able to notify on build failure and success

One can gather valuable insights about the engineering rigor, team, product, and company by examining the source code and build pipelines. It is important to watch out for certain antipatterns, including:

1. Absence of pipeline for continuous integration and deployment (CI/CD).
2. Pipelines written solely in shell scripting or running as shell steps.
3. Confusingly named pipelines that make it difficult to understand their purpose.
4. Lack of adherence to code quality, security, or other best practices.
5. Storing build artifacts on the build system itself instead of a proper artifact repository.
6. Overly complex pipelines with numerous steps and obscure tools, resembling a Rube Goldberg machine.
7. Pipelines that do not provide feedback, status, or silently hide failures.
8. Hosting pipelines on a single machine or build node that serves multiple purposes, leading to potential conflicts and inefficiencies.
9. Absence of retries or timeouts in both the code and pipelines.
10. Overcomplicating the pipeline logic by hiding its complexity within a convoluted library.
11. No consideration for security in the code or pipelines, including the absence of security related stages.
12. Manual pipelines with an excessive number of build parameters (100+ in some cases 😁 ).

It is important to be aware of these antipatterns, as they can indicate potential issues and areas for improvement in the development proce
